## 1. 关键变更说明

相对需求文档 V1.0，经项目组确认作以下调整：

| 编号 | 变更项 | 需求文档原方案 | 调整后方案 | 原因 |
|------|--------|---------------|-----------|------|
| C1 | 终端范围 | PC 网页 + 管理后台 | PC 用户端 + 管理后台 + 商家后台 | 覆盖完整演示链路 |
| C2 | 后端技术栈 | 未指定（架构图含网关+微服务） | Node.js 20 LTS + TypeScript + MidwayJS/Cool Admin 模块化单体 | 与现有 `app/cool-admin-midway` 工程一致，单体共享公共服务层集成风险最低 |
| C3 | 架构形态 | API 网关 + 6 个独立服务 | 单一可部署的模块化单体，预留拆分演进路径 | 学生团队联调与部署成本可控 |
| C4 | 第三方服务 | 微信支付/短信/OSS/内容审核真实对接 | 统一抽象接口 + Mock 实现，MinIO 本地替代 OSS | 商户资质与费用限制，答辩时可切换真实服务 |

> 需求文档中“小程序端功能”章节的一期功能由 H5 响应式页面承接；微信小程序代码、审核流程和小程序专属 API 不属于一期验收范围。

## 3. 总体架构

### 3.1 架构图

```
┌─────────────────────────────────────────────────────┐
│ 浏览器：PC 网页端 / 管理后台 / 商家后台（Vue3 SPA）   │
└──────────────────────┬──────────────────────────────┘
                       │ HTTPS / JSON
┌──────────────────────▼──────────────────────────────┐
│ Nginx：静态托管三套前端 + /api 反向代理到后端          │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│ MidwayJS + Cool Admin 模块化单体（可多进程部署）        │
│  ┌──────┬──────┬──────┬──────┬──────┬──────┐        │
│  │ m1 衣 │ m2 食 │ m3 住 │ m4 行 │ m5 社区 │ 后台 │ │
│  └──┬───┴──┬───┴──┬───┴──┬───┴──┬───┴──┬───┘        │
│  ┌──▼──────▼──────▼──────▼──────▼──────▼────────┐   │
│  │ wudong/common 公共服务层：认证/订单/购物车/支付/│   │
│  │ 上传/收藏/消息/搜索/敏感词/操作日志（common + Cool Admin）│ │
│  └───────────────────────┬──────────────────────┘   │
└──────────────────────────┼──────────────────────────┘
                           │ TypeORM / Redis / MinIO SDK
┌──────────────────────────▼──────────────────────────┐
│   MySQL 8（单库多表）  Redis 7  MinIO（本地对象存储） │
└─────────────────────────────────────────────────────┘
```

### 3.2 架构决策：模块化单体

**为什么不采用需求文档中的微服务方案：**

1. 6 组学生并行微服务开发，接口契约、服务间调用、分布式事务（订单-支付-库存）风险极高
2. 公共服务（用户/订单/支付）通过 Midway IoC 注入共享，无需 RPC
3. 单一可部署应用便于本地开发、容器部署和集成联调；生产环境可使用多个 worker
4. 模块间通过 TypeScript 模块边界隔离，后续如需拆分，按模块平移为独立服务即可

**模块化单体的三条纪律：**

| 纪律 | 要求 |
|------|------|
| 包边界 | `wudong/mX` 只能依赖本模块、`wudong/common` 与 Cool Admin 公共 API；`common` 不允许依赖任何 `m1-m5` |
| 表边界 | 模块只能读写本模块表 + 公共表；跨模块数据通过公共接口获取 |
| 路由边界 | 路由前缀 `common/ m1/ m2/ ... m5/` 与模块一一对应；后台管理接口沿用 Cool Admin 既有前缀 |

## 4. 代码仓库与工程结构

### 4.1 仓库策略

- 单 Git 仓库（Gitee/GitLab）monorepo，统一管理前后端与部署配置
- 仓库名：`wudong-platform`
- `CODEOWNERS` 文件划分各目录归属，PR 必须经归属组 review



### 4.3 模块包内部统一分层

每个模块包（m1-m5）内部固定四层，禁止跨层乱调：

```
modules/wudong/mX/
├── config.ts                  # 模块注册
├── entity/                    # 本模块 TypeORM 实体（仅本模块表）
├── dto/                       # class-validator 入参/出参 DTO
├── controller/{app,admin}/    # 薄层：参数绑定/校验 + 调用 service
└── service/                   # 业务逻辑（可注入 common，不可依赖其他业务模块）
```

`app/cool-admin-midway/src/modules/base`、`user`、`task` 等为 Cool Admin 框架模块，业务开发不得直接复制或修改其源码。乌东业务统一位于 `src/modules/wudong/`；P1 维护 `wudong/common`，P3-P5 分别维护 `m1-m5`，P6 只通过现有 Cool Admin 菜单、角色与数据权限扩展后台。

## 7. API 设计规范

### 7.1 路由与风格

- 风格：RESTful；前缀统一为 `/api/v1/{common|m1|m2|m3|m4|m5}/...`
- 示例：`GET /api/v1/m1/goods?page=1&page_size=20`、`POST /api/v1/common/orders`
- 动词规范：GET 查询、POST 创建/操作、PUT 全量更新、PATCH 部分更新、DELETE 删除（默认逻辑删除）
- 全部接口必须有：DTO 入参模型、出参模型、Midway/Cool Admin Swagger 描述、至少一个 `example`（验收要求接口文档完整）
- 分页统一使用 `page`、`page_size`，默认 20、最大 100；时间使用 ISO 8601；金额使用字符串表达
- 写操作支持 `Idempotency-Key`；服务端保存幂等结果至少 24 小时
- 所有响应和日志带 `X-Request-ID`；错误响应统一包含 `request_id`

### 7.2 统一响应体

```json
{ "code": 0, "message": "ok", "data": { } }
```

- `code = 0` 成功；非 0 为业务错误码；HTTP 状态码仍遵循语义（401/403/404/422/500）
- 列表分页统一：`{ "items": [], "page": 1, "page_size": 20, "total": 128 }`

### 7.3 错误码分配

| 段 | 归属 | 示例 |
|----|------|------|
| 0 | 成功 | — |
| 1xxx | 公共基础 | 1001 未登录/登录过期、1002 无权限、1003 资源不存在、1004 参数错误、1005 请求过于频繁、1006 资源冲突 |
| 2xxx | 用户与认证 | 2001 验证码错误、2002 手机号已注册、2003 密码错误 |
| 3xxx | 订单 | 3001 订单状态不允许该操作、3002 库存不足 |
| 4xxx | 支付 | 4001 支付单不存在、4002 支付金额不符 |
| 5xxx | 购物车 | 5001 商品已失效 |
| 6xxx | 上传与审核 | 6001 文件类型不允许、6002 文件过大、6003 内容审核未通过 |
| 71xx | 模块 1 | 各组在各自段内自定并维护错误码表 |
| 72xx | 模块 2 | 同上 |
| 73xx | 模块 3 | 同上 |
| 74xx | 模块 4 | 同上 |
| 75xx | 模块 5 | 同上 |
| 76xx | 预留 | 暂不使用；后台业务错误码沿用 Cool Admin 约定 |
| 9xxx | 系统 | 9001 系统内部错误、9002 第三方服务不可用 |

### 7.4 鉴权约定

- 请求头 `Authorization: Bearer <JWT>`；JWT 有效期 2h，过期后走刷新接口
- JWT 必须包含 `sub`、`jti`、`iat`、`exp`、`iss`、`aud`；refresh token 只存数据库哈希，刷新时轮换并撤销旧令牌
- refresh token 通过 HTTPS 下的 HttpOnly、Secure、SameSite cookie 传输；access token 仅存前端内存，禁止写入 localStorage
- 后端提供统一的 Midway IoC 鉴权上下文（第 6 组在 `wudong/common` 提供）：
  - `get_current_user`（登录用户）
  - `get_current_merchant`（商家，含店铺数据隔离校验）
  - `get_current_admin`（管理员，含 RBAC 权限校验）
- 模块接口需要用户身份时**一律使用上述依赖**，禁止自行解析 token

### 7.5 接口文档

- Cool Admin Swagger 模块提供 `/swagger`（以当前工程配置为准），作为各组联调的活文档
- 公共服务契约变更需在 PR 中标注 breaking change 并同步各组
- 期末交付 OpenAPI JSON 导出文件（验收要求）

## 8. 公共服务接口契约（第 6 组交付）

### 8.1 交付节奏

| 节点 | 交付物 | 验收口径 |
|------|--------|---------|
| 第 1 周周末 | 公共表 DDL + 鉴权可用 + 全部公共接口 OpenAPI 契约（含响应示例） | 各组能注册/登录，能根据契约写前端代码 |
| 第 2 周周末 | 购物车/订单/支付/上传/收藏/消息/搜索全部 mock 打通 | 全链路演示：下单→模拟支付→订单状态流转 |

### 8.2 接口清单（概要）

**用户与认证**
- `POST /api/v1/common/auth/sms-code` 发送验证码
- `POST /api/v1/common/auth/register` 注册
- `POST /api/v1/common/auth/login` 密码登录 / `POST /api/v1/common/auth/login-sms` 验证码登录
- `POST /api/v1/common/auth/refresh` 刷新 token
- `GET /api/v1/common/users/me`、`PATCH /api/v1/common/users/me` 个人信息
- 收货地址 CRUD：`/api/v1/common/users/me/addresses`
- 收藏：`GET/POST/DELETE /api/v1/common/favorites`（按 target_type 过滤）
- 商家入驻申请：`POST /api/v1/common/merchant/apply`、`GET /api/v1/common/merchant/apply/{id}`

**购物车（实物类：模块 1 + 模块 2 特产）**
- `GET /api/v1/common/cart`、`POST /api/v1/common/cart`、`PATCH /api/v1/common/cart/{id}`、`DELETE /api/v1/common/cart/{id}`、`POST /api/v1/common/cart/check`（库存校验）

**订单中心**
- `POST /api/v1/common/checkouts`（购物车结算并按商家/模块拆单）
- `POST /api/v1/common/orders`（非购物车预订类订单创建）
- `GET /api/v1/common/checkouts/{checkoutNo}`、`GET /api/v1/common/orders`、`GET /api/v1/common/orders/{orderNo}`
- `POST /api/v1/common/orders/{orderNo}/cancel`、`/confirm`（商家确认）、`/complete`
- `POST /api/v1/common/orders/{orderNo}/refund`（申请退款，附原因和金额）
- 模块侧订单扩展数据由订单中心在同一事务内调用模块适配器写入；跨请求动作通过订单事件表和异步任务可靠投递（见 8.3）

**支付**
- `POST /api/v1/common/pay/{orderNo}` 发起支付（返回 mock 支付凭证）
- `POST /api/v1/common/pay/{payNo}/mock-confirm` 模拟支付成功（仅开发环境，必须校验订单归属、金额和当前状态）
- `GET /api/v1/common/pay/{orderNo}/status` 支付状态查询

**上传与审核**
- `POST /api/v1/common/upload/image`（≤5MB，jpg/png/webp）
- `POST /api/v1/common/upload/video`（≤100MB，≤60s，mp4；由 FFprobe 校验时长）
- 返回 `{file_id, status, url, thumb_url, audit_status}`；缩略图和审核异步生成，审核不通过的内容由消息接口通知

文件状态统一为 `INITIATED`、`UPLOADED`、`PROCESSING`、`READY`、`REJECTED`、`DELETED`；上传未完成超过 24 小时的记录由定时任务清理。原图默认私有，签名 URL 有效期不超过 1 小时；公开内容只返回缩略图或短期签名地址。

**消息**
- `GET /api/v1/common/notify/messages`、`POST /api/v1/common/notify/messages/{id}/read`、`POST /api/v1/common/notify/messages/read-all`
- 模块触发消息：`POST /api/v1/common/notify/send`（内部调用，如订单状态、互动提醒）

**搜索**
- `GET /api/v1/common/search?keyword=&type=GOODS|RESTAURANT|HOUSE|SCENIC|ROUTE|POST`
- `GET /api/v1/common/search/hot` 热搜词

**首页运营**
- `GET /api/v1/common/home/banners`、`GET /api/v1/common/home/announcements`、`GET /api/v1/common/home/recommends`

### 8.3 订单事件与异步任务机制

订单领域事件采用“TypeORM 事务内落库 + `@cool-midway/task` 异步投递”，不直接依赖内存回调保证一致性。第 6 组提供 `wudong/common/service/order-events.ts` 和 `schedule/`：

```typescript
// 模块在配置或初始化事件中注册
import { OrderEventRegistry } from '../common/service/order-events';

registry.register(
    order_type="LODGING",
    on_order_created=...,   # 同一事务内：模块写 t_mX_order_ext、创建库存预占
    on_order_paid=...,      # 支付成功后：模块生成电子票/预订生效
    on_order_cancelled=..., # 取消后：模块释放资源
    on_refund_approved=..., # 退款成功：模块回滚资源/核销电子票
)
```

- 订单创建事务必须同时写入 `wudong_common_order_event`，事件状态为 `PENDING`；事务提交后由任务队列投递。
- 消费者必须按 `event_id` 幂等；失败按 1、5、30 分钟递增重试，超过 5 次进入死信队列并发送管理员告警。
- 库存释放、订单超时取消、支付状态查询、消息发送、文件缩略图和内容审核均使用 `@cool-midway/task` 或 Midway Cron，不阻塞 API 请求。
- 第 6 组提供 Midway 配置/初始化入口，各组在 `wudong/mX/config.ts` 中完成可重复的模块注册。
- 模块间不允许互相直接调用；跨模块联动（如路线套餐含住宿）通过公共接口或事件完成；一期路线不做跨模块库存编排。

## 9. 第三方服务抽象层

统一放在 `src/modules/wudong/common/provider/`，通过配置切换实现：

```typescript
# `app/cool-admin-midway/src/config/config.default.ts` 中配置
PAYMENT_PROVIDER=mock        // mock | wechat
SMS_PROVIDER=mock            // mock | aliyun
STORAGE_PROVIDER=minio       // minio | aliyun_oss
AUDIT_PROVIDER=local         // local | aliyun_green
```

| 抽象 | 接口（要点） | Mock 实现行为 | 真实实现预留 |
|------|-------------|--------------|-------------|
| PaymentProvider | create_payment / query / refund / parse_callback | 仅开发环境开放 `mock-confirm`；必须校验当前用户、订单未过期、支付金额和订单状态 | WechatPayProvider 骨架类，包含签名校验、金额校验和回调幂等位 |
| SmsProvider | send_code / send_template | 验证码固定 `123456` 并打印到后端日志；不实际发送 | AliyunSmsProvider 骨架 |
| StorageProvider | create_upload / complete / delete / presign | MinIO 本地容器即为真实可用；完成上传后异步生成缩略图 | aliyun_oss 骨架 |
| AuditProvider | check_text / check_image | 本地敏感词过滤（DFA + `wudong_common_sensitive_word` 词库）；图片默认进入人工审核队列 | 阿里云内容安全骨架 |

**规则：** 业务模块一律面向抽象接口编程，禁止直接 import mock 实现类；切换真实服务只改配置不改业务代码。

## 10. 前端开发规范

### 10.1 工程与路由

- 用户端单独构建；管理端统一使用 `app/cool_admin_vue`，通过角色、菜单和数据权限区分管理员与商家
- `packages/api` 或用户端 API 层提供全部后端接口封装（TypeScript 类型与后端 DTO/OpenAPI 契约对应），页面内**禁止裸写 axios 调用**，统一走 API 层
- 路由归属见 5.1 分工表；主站路由：

```
/                    首页（公共前台）
/login /register     登录注册（公共前台）
/goods/*             衣（第1组）
/food/*              食（第2组）
/stay/*              住（第3组）
/trip/*              行（第4组）
/community/*         社区（第5组）
/cart /orders /user/*  购物车、订单、个人中心（公共前台，聚合页）
```

### 10.2 约定

| 项 | 约定 |
|----|------|
| 响应式 | 断点：<768 移动、768-1280 平板、≥1280 桌面；主站全部页面必须适配移动端（承接一期 H5 功能） |
| 主题 | 全局主题变量（民族风主色、圆角、字号）定义在 `packages/shared`，三套 Web 应用统一引用，禁止页面内硬编码颜色 |
| 状态管理 | Pinia store 按模块拆分（goodsStore、cartStore、orderStore…）；登录态/用户信息用共享 store |
| 鉴权 | axios 拦截器统一注入 token；code=1001 时清除登录态跳登录页 |
| 图片 | 一律使用上传接口返回的 URL；列表用 `thumb_url`，详情页才用原图（性能要求：缩略图 ≤200KB） |
| 错误处理 | 统一从响应 envelope 解析 code/message，ElMessage 提示；错误码映射文案集中在 shared |
| 富文本 | 详情富文本渲染使用白名单过滤后的 HTML（服务端已过滤，前端仍需 v-html 前二次消毒，或使用组件库内置渲染组件） |
| 代码质量 | ESLint + Prettier 统一配置放仓库根；CI/提交前检查 |

## 11. 安全规范

| 类别 | 要求 | 实现位置 |
|------|------|---------|
| 密码存储 | bcrypt（cost = 12），禁止明文/可逆加密 | `wudong/common` / Cool Admin 用户模块适配 |
| 认证 | JWT access token + 数据库哈希 refresh token；刷新轮换并支持撤销；敏感操作（支付/退款/改密）二次验证 | common |
| 权限 | 复用 Cool Admin RBAC；商家数据隔离（中间件/上下文强制校验商家只能访问自家资源） | common + Cool Admin middleware |
| 注入防护 | 全部 SQL 走 TypeORM 参数化查询；禁止字符串拼接 SQL | 全局 |
| XSS | 富文本服务端白名单标签过滤；前端 v-html 前二次消毒 | common + shared |
| CSRF | access token 不放 Cookie；refresh token Cookie 接口校验 Origin/Referer 和 CSRF token；仍禁止 GET 执行写操作 | 全局 |
| 越权 | 资源归属校验：查询/操作带 user_id、merchant_id 的资源时必须校验归属 | 各模块 service |
| 脱敏 | 手机号 138****1234、身份证只显前 4 后 4；接口输出层统一脱敏工具 | shared/common |
| 上传安全 | 扩展名白名单 + 文件头魔数校验 + 大小限制 + FFprobe 视频校验；文件随机命名，禁止用户可控路径 | common |
| 内容安全 | 文本/图片过审核接口；敏感词库管理在 admin；命中 3 次自动禁言 24h（需求 11.5） | common + m5 |
| 审计 | 管理员全部写操作记录操作日志（操作人/IP/对象/内容，保留 1 年） | common + Cool Admin |
| 密钥 | JWT_SECRET、数据库密码等放 .env，不入库；仓库只提交 .env.example | 全局 |
| 限流 | 登录/验证码/支付/退款/上传接口按 IP、用户和手机号组合限流；连续失败触发短时锁定 | common |

## 12. 编码与 Git 协作规范

### 12.1 编码规范

**TypeScript 后端（`mwts` 强制，配置在 `app/cool-admin-midway`）：**
- 开启严格类型；DTO、Entity、Service 的公开方法必须声明类型
- 禁止 `any`、空 `catch`、`console.log`（使用 Midway Logger）
- 模块间依赖方向：`mX → common → Cool Admin 公共 API`，禁止反向
- 提交前本地必须通过 `npm run lint` 与 `npm test`

**TypeScript：**
- ESLint + Prettier 统一规则（仓库根配置）；组件用 `<script setup lang="ts">`
- 目录：`src/views`（页面）、`src/components`（本应用组件）、`src/stores`、`src/router`
